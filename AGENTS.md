# AGENTS.md

## Direction: the defaults do nothing, and a first run says so

Every behavior is off by default — `shouldHandleRenames` AND `shouldRenameAttachmentFolder` included, because the attachment move runs with link updates off. Custom Attachment Location and Consistent Attachments and Links declare this plugin as a mandatory dependency (`getPluginDependencies()` in `obsidian-dev-utils`), so users are made to install it, and being made to install something must not change how their vault behaves. Their old values arrive through `migrateSettings`, where the user sees what would change. Do not turn a default back on to make a demo or a test simpler; set it explicitly there.

The price is one user the defaults would silently switch off: someone upgrading from 1.x who never changed a setting, so nothing of theirs is on disk to keep. A missing `data.json` cannot tell them apart from a fresh install, so `src/first-load-notice-component.ts` tells both, once, and then leaves a `data.json` behind. It writes `{}` through `ensureDataFileExists` rather than calling `saveToFile`, because the library's `saveToFile` skips a save when nothing changed since the read — which on a first run is always. `src/first-load-notice.cross-platform.integration.test.ts` is what caught that; a unit test with the settings component mocked cannot. Since `obsidian-dev-utils` 107.0.0 the library's own first load writes the full default record when it finds no `data.json`, so by the time the notice asks, the file is usually there already and `ensureDataFileExists` writes nothing; `wasDataFileMissingOnInitialLoad` is captured on that first read, so the notice still fires.

The settings tab lists the plugins that depend on this one, from the `dependencyPluginIds` of their `obsidian-dev-utils:plugin-loaded` broadcasts (`src/plugin-dependents-component.ts`). It subscribes in `onloadImpl`, before `getPluginApis()` publishes the API that a dependent's gate waits for, so no dependent can announce itself unheard. The API is published through `getPluginApis()`, not by hand, for that reason and so the broadcast carries the contract version.

## Direction: stay Advanced-Exclude-agnostic; the fix is the disk-existence guard

This plugin must NOT couple to Advanced Exclude — no `app.advancedExclude`, no "bulk in progress" signal handshake. (In `obsidian-consistent-attachments-and-links`, which owned this handler before, a prototype gating the settings builder's `isPathIgnored` on `app.advancedExclude.isApplyingProjection` was committed then reverted precisely to keep the plugin agnostic.)

The bulk-deletion freeze was caused by the delete handler acting on **index-only removals** — a synthetic `vault.on('delete')` where the file still exists on disk (e.g. when a folder is hidden). The agnostic fix skips the handler when `await this.app.vault.adapter.exists(this.file.path)` is true. It lives in `DeleteHandler.handle()` in `src/rename-delete-handler-component.ts` rather than in the settings builder's `isPathIgnored`, because `isPathIgnored` is synchronous and the existence check is awaited.

## The published API is declared once, in the root `api.d.ts`

`api.d.ts` is the file a consumer copies, so it imports NOTHING — not `obsidian-dev-utils`, not a sibling module — and `src/plugin-api.ts` re-exports its types rather than declaring them, keeping only the runtime contract and `PLUGIN_API_VERSION`. The README links it instead of re-typing the interface; edit the file, not a prose copy of it.

- **`EmptyFolderBehavior` is a string-literal union there, and the library's enum everywhere else.** A string enum is nominal, so the enum is assignable to the union and not the reverse. The two are held together by `EMPTY_FOLDER_BEHAVIOR_BY_API_NAME` in `src/settings-migration.ts`, a `Record` keyed by the published union, plus `PluginApiImpl.getSettings` handing the enum out as the union. That is the ONLY compile-time check the inlined union gets: `skipLibCheck` means a declaration file is never checked from the inside. Do not replace the record with a cast.
- **There is no `api` getter on the plugin instance, deliberately** (retired 2026-09-23). It handed a consumer whatever version was installed, with no negotiation, no contract check and no revocation, and it made the registry's guarantees optional for anyone who took the shorter path. A consumer without the library reads the registry directly, per the Plugin API protocol guide the README links. `src/plugin.test.ts` pins its absence; do not bring it back as a convenience for a test — the integration suites read the registry record for exactly that reason.

## Integration tests

`src/bulk-delete.desktop-performance.integration.test.ts` (vitest project `integration-tests:desktop-performance`, run via `npm run test:integration:desktop:performance`) guards both halves. It seeds `shouldHandleDeletions` and two folders of notes through `scripts/generate-performance-vault.ts` / `scripts/vitest-global-setup-performance.ts`, and installs its own counting, delaying `app.vault.getAvailablePathForAttachments.extended` stub standing in for Custom Attachment Location — so the bottleneck is provable without a 90k-file vault. Ported from `obsidian-consistent-attachments-and-links` at `31678aa^`, when that plugin stopped registering a handler and both of its arms started measuring zero.

- **O(N) reproduction**: a bulk **real** deletion (`trashFile`) of N notes resolves the attachment path exactly once per note — and zero times with the plugin disabled. Real deletions are inherently O(N); the fix does not (and must not) change this.
- **Index-only-removal skip**: firing one `vault.on('delete')` per note **without** removing it from disk must resolve **zero** attachment paths, because the disk-existence guard skips every synthetic removal. A single real deletion enqueued last is the FIFO drain marker proving the synthetic handlers actually ran.

The note count defaults to 200 and is overridable via `RENAME_DELETE_PERF_VAULT_NOTE_COUNT` for a quicker (smaller) or harsher (larger) run.

`src/delete-walk.desktop-performance.integration.test.ts`, in the same project, counts the same walks for a protected folder delete: 20 attachments a note outside the folder embeds, plus one nothing embeds. It asserts zero walks, and that the unlinked file is deleted while the 20 embedded ones stay. Before the pre-passes went through `BacklinkIndex` the same delete took 43; with them on it and the library still walking once per file it visited, it took 1, because that walk stopped at the first child it kept. `obsidian-dev-utils` 107.0.0 visits every child and answers its own lookups from an index, and the delete measures 0 (2026-09-25).

`src/rename-walk.desktop-performance.integration.test.ts`, in the same project, guards the rename side. It wraps `metadataCache.iterateAllRefs`, renames a seeded folder of 40 notes with `shouldHandleRenames` on (also seeded in that `data.json`), and asserts **at most one** whole-vault walk. The one walk is Obsidian's own `runAsyncLinkUpdate`. Before `BacklinkIndex` the same rename took 2F + 1 = 81 walks, and pointing the index back at `getBacklinksForFile` fails the suite at exactly 81. It also asserts that every link in five holder notes still resolves afterwards. Those links name the moved notes by full path, and the handler suppresses Obsidian's own rewrite of them, so an index that missed a backlink leaves a link broken. An index that answers nothing fails it that way.

`src/base-rename.desktop-performance.integration.test.ts`, in the same project, renames a base that 903 notes reference (issue #3) and asserts that every reference follows it and that nothing reaches `console.error`. The base sits in a subfolder, with spaces and parentheses in its name, and the referencing notes cycle through six reference shapes: bare name, view subpath, full path, alias, markdown embed, and frontmatter link. It passes on this plugin's 1.3.0 bundle as well, and also with Custom Attachment Location 12.0.1 enabled beside it (measured 2026-09-24). So it guards the scale and the shapes, but it does not reproduce the report. The reporter's video shows this plugin's *unhandled error* notice partway through the rewrite, and that error is in a vault this suite cannot copy.

### Backlink lookups go through `BacklinkIndex`, never `getBacklinksForFile`

Obsidian's `metadataCache.getBacklinksForFile` is not an index lookup. It is a full `iterateAllRefs` walk with one `getFirstLinkpathDest` per reference, about 115 ms at 100k references. The handler asked it twice per renamed file: once synchronously inside the vault `rename` event, and once in the queued `refreshLinks`, plus once per moved attachment. A 1000-note folder rename in a 50k-note vault took 924 s, and the renderer did not answer for minutes (measured on 1.14.2, 2026-09-24). `src/backlink-index.ts` gives the same answer from the notes that could hold a backlink. Its header has the argument. In short, every branch of `getLinkpathDest` only returns a file whose name matches the linkpath's last segment, so an index keyed by that segment finds a superset of the backlinks. Obsidian's own predicate then filters that superset. The index stays fresh by comparing each note's `fileCache` hash on every query, not by listening to events, so it cannot miss an event or see them in the wrong order.

- **Do not reintroduce `getBacklinksForFileOrPath` / `getBacklinksForFileSafe` from the library on the rename or delete path.** `BacklinkIndex.getBacklinksForFileSafe` mirrors the library's save-and-verify loop around the index lookup, because that loop calls `getBacklinksForFileOrPath` from inside the library, where it cannot be redirected.
- **The verify loop takes a canvas holder as current without reading it, and the library's does not.** Obsidian's canvas index reports a text-node embed with a position, but that position is an offset into the node's own text. Slicing the canvas JSON there never gives the embed back, so the loop retried forever. Moving a canvas whose text node embedded its attachment held the queue for good (measured 2026-09-24, pinned by `canvas-text-node-attachment-move.cross-platform`). The library's loop escapes only when a file-node reference comes first, because it stops at the first reference of neither kind.
- **A backlink-cache plugin's `safe` overload still wins** when one is installed, exactly as in the library. Backlink Cache is being retired, and when it is gone nothing in this plugin gets slower: the index does not depend on it.
- **Deletion walks nothing.** `findSurvivingNotePaths`, which both folder-delete pre-passes call (the protection pre-scan and `rescueStillUsedUnitFolders`), goes through the same `BacklinkIndex`. The library's `deleteIfNotUsed` calls its own `getBacklinksForFileSafe` once per file it visits, and since `obsidian-dev-utils` 107.0.0 that answers from the library's own backlink index rather than a walk.
- The `linkUpdaters` side (canvases) is still walked in full per query. Canvas references live in the canvas index, not in `fileCache`, so there is no hash to key them by. A vault's canvases hold a small fraction of its references.

> The integration tests run the built bundle in `dist/build`, not `node_modules`. Run `npm run build` first after any source or `obsidian-dev-utils` change, or they silently exercise the stale bundle.

### `flushQueue()` goes AFTER the effect you are waiting for, never straight after the rename

`flushQueue` appends a no-op to the operation queue and awaits the queue's promise chain, so it only covers what is **already enqueued at the moment it is called**. The handler enqueues its work from the vault's `rename` / `delete` event — i.e. *after* `app.fileManager.renameFile(...)` has resolved. A suite that calls `flushQueue()` on the line after the rename therefore drains an **empty** queue and returns in microseconds, having waited for nothing, and then reads vault state while the operation is still in flight.

It fails intermittently rather than always, which is what makes it dangerous: `canvas-partial-write-guard` passed 2 of 3 isolated runs that way, and the third read a transiently re-serialized canvas. The order that actually works is: rename → `waitUntil` the observable effect (the moved attachment), which proves the operation is underway → **then** `flushQueue()`, which now waits for the remainder of that same operation → then assert.

Do not paper over this with a longer timeout on an unrelated wait. `canvas-partial-write-guard` was green for exactly that accidental reason — a 10-second wait for a notice that never appeared — and deleting the dead wait is what exposed the race underneath it.

**The ordering rule stands, but the re-serialized canvas was never its symptom** (measured 2026-09-24). The canvas that suite kept catching in Obsidian's tab-indented, one-node-per-line format was not a transient copy caught mid-operation. It was the file's final state, and **Obsidian** wrote it. The handler hands every link update whose source is a canvas back to Obsidian's native updater, and that updater (`applyUpdates` in the canvas link updater) rewrites only text nodes but re-serializes the whole file every time it runs. It runs whenever Obsidian's canvas index already holds the canvas when the attachment moves. For a canvas created milliseconds earlier that is a race against the indexer, which the index usually lost, so the suite passed. It failed about one desktop aggregate in three, and every time once the suite waited for the index first. So the suite now waits for the index and asserts that no canvas write came from **this plugin**, identified by a `plugin:<id>` frame in the write's stack. It no longer asserts byte-identity. Removing the guard from the built bundle fails that assertion on desktop and on Android alike. The parsed canvas may still differ in one field, the file node's path, because Obsidian's canvas plugin re-points a file node at a moved file on its own schedule. That landed before the read in one Android run of two.

**That suite, and every one that moves a file a canvas links, sets `alwaysUpdateLinks: true` itself, Android included.** With it off, the canvas link update the handler hands back to Obsidian reaches `updateAllLinks`, which opens its *Update links* confirmation and awaits an answer. Headless, nobody answers, so the attachment's `renameFile` never returns and this plugin's queue is held behind it. The harness turns the setting on, and since `obsidian-integration-testing` 17 that default reaches the Android device too (earlier Android transports lost it before the vault opened, which is why `rename-link-update` and the Android capture suite used to set it themselves). **Since 2026-09-24 the handler answers that confirmation itself for every canvas entry it hands back while `shouldHandleRenames` is on** (`updateAllLinksWithoutPrompt` in `src/rename-delete-handler-component.ts`, pinned with the setting off by `canvas-link-update-prompt.cross-platform`). It already rewrites every other link without asking, so a prompt that appeared only when a canvas was involved, and asked about an attachment the user never moved, was an artifact of the hand-back. Entries handed back because a path is *ignored* still prompt, because "ignored" means Obsidian's own behaviour applies. The suites keep the setting on so each measures its own subject; the prompt has one suite of its own. That looked like Obsidian's link updater hanging on the rewritten partial canvas until it was measured on 2026-09-24. With the plugin disabled, the same indexed move finishes in under 250 ms on a partial canvas and on a valid one, and with `alwaysUpdateLinks` left off the modal is on screen. So the handler needs no guard against a native update that never returns: this one returns as soon as the user answers. The two `canvas-partial-write-guard` observations quoted in this section and under *Effects arriving is NOT the queue being empty* are most likely this index race rather than the ordering race. The rule is still right on its own reasoning, and `rename-link-update`'s half-read link is still its evidence.

### A suite hands back the plugin settings it staged, because they outlive the file

One `npm run test:integration:desktop` (or `:android`) drives **every** suite against **one** Obsidian instance. The vault is temporary and fresh per run, but the app — and with it the loaded plugin and the settings it holds — outlives each test file. Eleven suites write settings through `api.migrateSettings` to stage what they are about to test, and their `finally` blocks put back `attachmentFolderPath` and `alwaysUpdateLinks` while leaving the plugin settings exactly where they left them.

That would be survivable if the file order were fixed. It is not: vitest's default sequencer runs previously **failed** files first and then previously **slowest** first, from a cache every run rewrites — so the order changes run to run with nothing in the repo changing. `shared-attachment-tie` stages exactly the two values `settings-migration` proposes (`notePriorities: ['.md']` plus `shouldHandleDeletions: true`), so whenever it sorted ahead, that proposal changed nothing, `PluginApiImpl.migrateSettings` returned on its `rows.length === 0` path **without opening a dialog**, and `settings-migration` spent 20 seconds waiting for a dialog that was never coming. That was the aggregate failing about half its runs, on `main` as readily as on any branch.

So every settings-driving suite snapshots in `beforeAll` and hands back in `afterAll`, through `src/settings-snapshot.integration-helper.ts`. Give any new suite that writes settings the same pair. And never write a `waitUntil` that *insists* on the migration dialog: a proposal matching what the plugin already holds opens none, so settle on `isSettled || document.querySelector('.modal-container') !== null` the way each suite's `applySettings` helper does.

### The rename/delete regression suites, and how they were ported

Seven suites came from `obsidian-custom-attachment-location` when it stopped registering a rename/delete handler; each pins a real reported issue against that plugin's tracker, and each one's header names its issue. Six landed as files, the seventh was folded into an existing one:

| Suite | Pins |
| --- | --- |
| `rename-alias-refresh.cross-platform` | #20 — an alias equal to the old base name is refreshed to the new one |
| `canvas-attachment-move.cross-platform` | #22 — moving a `.canvas` moves an attachment found via its own references |
| `canvas-partial-write-guard.cross-platform` | #45 — a partial `.canvas` is never written back to disk |
| `foreign-locked-folder-swap.desktop` | #49 — every rename of another plugin's locked transaction is left alone |
| `note-move-many-attachments.desktop` | #60 — moving a note leaves every embed resolving, at 3 and at 30 |
| `note-move-concurrent-edit.desktop` | #60 — and still does when an outside edit lands mid-rename |
| `native-link-update-fallback.cross-platform` | #47 — its first case absorbed the phantom-old-path assertion |

Three substitutions were forced, and they are the things to preserve when editing any of them:

- **Settings go in through the published API's `migrateSettings` and its approval dialog**, not by assignment. Every closure reaches that API the way a library-free consumer does — the first unrevoked record at `globalThis.__obsidianDevUtils.pluginApiRegistry.value.records[pluginId]` — because the plugin instance carries no `api` member. The originals walked the owning plugin's component tree to find a live settings object; this plugin's only public write path is that API, so every suite carries the same `applySettings` helper (an `evalInObsidian` callback is serialized, so it cannot share one).
- **The attachment folder is Obsidian's own `attachmentFolderPath` vault config**, not the owning plugin's setting, and there is no equivalent of its per-note `${noteFileName}` token. So the ported scenarios use a SHARED `./assets` folder, and the note-move suites **move the note to another folder** rather than renaming it in place — that is what relocates a shared attachment folder, and (under `newLinkFormat: 'absolute'`) what makes every link name a folder that no longer exists until the handler rewrites it. The alternative, kept in reserve, is the `app.vault.getAvailablePathForAttachments.extended` stub the performance suite uses as a stand-in for that plugin.
- **Locks come from `lib.ResourceLockComponent`**, not from the library's realm-global bag: `lockForPath({ mode: 'subtree' })` under a foreign plugin id, and `isLockedByAncestorForPath` to report a rename's lock coverage.

Four of the seven were `it.skip` in their old home, for a shared-instance `renameFile`/`onCleanCache` stall in that plugin's much larger desktop aggregate. **None of them is skipped here** — measured, not assumed: the whole desktop aggregate runs 12 files / 17 tests in ~30s. The single remaining `it.skip` is documentation, in `canvas-partial-write-guard`, for the Advanced Canvas mid-initialization race that cannot be staged headlessly; it carries the manual recipe.

Two measurements worth keeping, because they contradict what the originals' comments claimed:

- `note-move-many-attachments` **cannot** reproduce the position-drift defect, and `note-move-concurrent-edit` is its only guard. Re-measured 2026-09-20: with `position` added to `getLinkIdentityKey`, the concurrent-edit suite fails with exactly the tail below its mid-note insertion and the many-attachments suite passes at both sizes. `editLinks` rewrites one holder from a single cache read, so a rewritten link growing shifts nothing that is looked up afterwards; only an outside edit between the snapshot and that read can. An earlier measurement here said the opposite — both sizes fully stale, 2026-09-02 — but that probe turned the concurrent-edit suite fully stale too rather than stale below its insertion, the signature of a key that matched no link at all. The many-attachments suite stays for the scale half of the report, at 3 and 30.
- `foreign-locked-folder-swap` **cannot** be broken from this repo: neutralizing this plugin's own foreign-lock skip in `handleRename` leaves it green, because both fixes it guards are `obsidian-dev-utils`'. It is a consumer-side guard over library behavior. Its lock-coverage assertion is live all the same — weakening the transaction's locks to `mode: 'file'` fails it, naming the three uncovered steps.

`scripts/vitest-config.ts` raises the desktop transport's `commandTimeoutInMilliseconds` to 240s for these. A whole `evalInObsidian` callback is ONE `Runtime.evaluate`, and the transport's 30s default kills a longer one while vitest is still waiting — reported as `CDP command timed out ... Runtime.evaluate`, naming neither the pending `waitUntil` nor the assertion that never ran. **That raise is a backstop, not a budget** — see the next section.

### A closure's declared waiting is summed against the transport's 30s DEFAULT, whatever this project's cap is

`obsidian-dev-utils/no-over-cap-wait-in-eval-in-obsidian` totals every `waitUntil` timeout, every `sleep`, and every bounded loop deadline written inside one in-Obsidian closure, and reports the closure when the SUM reaches 30 000 ms. Three things about that sum catch people out:

- **It is per CLOSURE, not per wait.** Four comfortable 8 000 ms ceilings are an over-cap closure. The number to write is the closure's whole allowance divided by however many charges it makes.
- **A helper declared inside the closure is charged once per CALL SITE.** An `applySettings` called at the top and again in a `finally` costs its budget twice; in `foreign-locked-folder-swap` it is five charges, because `runPhase` runs twice and each run both applies settings and waits for the cache. Divide by the call count, not by the number of `waitUntil` calls visible in the body.
- **It uses the DEFAULT 30s cap, with no per-project override.** The `desktop` project's raised 240s does not enter into it, and nothing would be gained if it did: the same cross-platform files run on Android under Appium's own ~30s, and `integration-tests:desktop-performance` raises nothing. A budget written against 240 000 is therefore red at lint time and false in two of the three projects.

A closure deliberately left under the cap says so, in a comment opening with the exact line `Under the transport's ~30s per-closure cap, not at it.` — the convention the rule documents, so a later sweep can tell a budget somebody read and kept from one nobody has looked at.

**When a wait genuinely needs more than the cap, it moves to Node** — `pollInObsidian`, with a short DOM- or vault-reading `poll`, the `until` predicate evaluated in Node, and the long budget in `timeoutInMilliseconds`. Four closures here needed it: the two note-move suites and both `bulk-delete` performance ones. A thirty-attachment move, or a two-hundred-note bulk delete through a serial queue at 25 ms a resolution, is minutes of real work by construction — so no ceiling small enough to fit one transport call is a ceiling a legitimate slow run survives, and lowering them would have traded an unreachable budget for a flaky one. In every case the long step is FIRED rather than awaited (`start` kicks it off, the `poll` is what proves it finished), and any page-side state the polls need — a fired rename's rejection, an emulated plugin's `EventRef`, an installed resolver's counters — travels through the call's `contextId`, which is what that parameter exists for.

**Effects arriving is NOT the queue being empty, and a converted suite still has to drain it.** The first draft of the note-move conversion dropped `flushQueue()` on the reasoning that the polls had replaced it. They had not: they prove the observable effects arrived, and the handler's queue can still hold tail work when the test's `finally` removes the fixture folders — which, since one run drives every suite against one Obsidian instance, becomes the NEXT suite's problem. Measured 2026-09-20: with the drain dropped, the desktop aggregate failed two runs out of two, each time in a different innocent suite reading a half-written file (`rename-link-update` reading a link the metadata cache had not yet re-read, `canvas-partial-write-guard` reading a transiently re-serialized canvas — the exact symptom the section above describes), against three green runs on the unchanged branch. Both suites call it from their `finally` now, so a failed assertion cannot hand a live queue on either. The ordering rule above is unchanged and is what puts it there: AFTER the effect being waited for, by which point what is left to drain is tail work that fits inside one transport call.

### The rescue-ambiguity dialog asks once per deletion, because the two asks OVERLAP

`src/shared-attachment-tie.cross-platform.integration.test.ts` pins the dialog that opens when several notes could adopt a stranded attachment and `notePriorities` names no single owner (Custom Attachment Location issue #71). Two things about it are easy to break:

- **It sets `attachmentFolderPath: './assets'`, a PER-NOTE subfolder, not a shared one.** With a shared folder both tied notes resolve to the same destination, the rescue is a no-op either way, and the test passes without proving anything.
- **It starts `trashFile` WITHOUT awaiting it**, waits for `.rescue-ambiguity-reason` to appear, clicks a button, and only then races `flushQueue()` against a second dialog. Awaiting the deletion first would deadlock — the deletion is what is waiting for the answer.

The deadlock that shaped `src/rescue-decision-scope.ts` is worth not re-deriving. `getRescuePath` is asked **twice** about one attachment in a folder deletion, and the asks **overlap**: `replayFolderDeletion` (not queued) deletes the owning note first, which enqueues that note's own `DeleteHandler`; the replay then reaches the attachment and awaits a dialog, and while it awaits, the obsidian-dev-utils queue runs the handler it just produced, which walks the deleted note's links back to the same attachment and asks again. Two dialogs open over one file, the user answers one, and the deletion never finishes. **A map of finished answers cannot fix this** — at the moment the second ask arrives there is no finished answer to find. So `RescueDecisionScope.resolveDecision` shares the *pending promise*: the second caller joins the first question. The scope's in-flight counter is entered **synchronously at enqueue time**, not inside the queued operation, which is what holds it above zero across the gap between the replay ending and the queue starting.

It lives in its own module rather than in `src/rename-delete-handler-component.ts` only because that file sits inside a `/* v8 ignore */` region and coverage is enforced at 100%.

**The dialog's button labels are disambiguated per note, not per dialog** (`src/note-path-labels.ts`, issue #1). A surviving note whose basename is unique among the ones offered keeps the bare basename; one whose basename collides grows the shortest trailing run of path segments that tells it apart from the notes it collided with, opening with an ellipsis when segments were dropped. Showing the full path on every button was considered and refused: it widens every button in every deep vault to fix a case most dialogs never reach, and the whole path is on the tooltip regardless — which is where the reporter found it before filing. The two cross-platform closures pin `Move to A.md` / `Move to B.md` on notes with distinct basenames, so they exercise the unique case and say nothing about the colliding one; that one is pinned in `src/rescue-ambiguity-modal.test.ts` and `src/note-path-labels.test.ts`.

A blocking modal inside a queued delete is safe: `addToQueue` passes `pluginNoticeComponent: null` to `runWithTimeoutNotice`, so the 60s timeout resolves to `onTimeoutWithoutNotice` — a debug log, no notice, and **no abort**.

### An attachment unit folder is moved BEFORE the walk, never by the per-file rescue hook

`src/attachment-unit-folder-rescue.cross-platform.integration.test.ts` pins the rescue of a whole attachment unit folder (Custom Attachment Location issue #70). The obvious implementation — have `didRescueStillUsedAttachment` move the folder when the hook names one — cannot work, and reading `deleteIfNotUsed` in `obsidian-dev-utils/obsidian/vault-delete` is what says so:

- It lists a folder's children **as paths** (`listSafe` → `adapter.list`) and walks them in order, files first. Inside a unit folder the linked attachment is one file among siblings.
- A sibling reached **before** it has no surviving backlink, so it is deleted outright — the unit is already gutted by the time the hook fires.
- A sibling reached **after** it no longer resolves, which reports the child as kept, so `canDelete` is false all the way up and the folder the user actually deleted is left standing.

So `rescueStillUsedUnitFolders` runs ahead of both walking `deleteIfNotUsed` calls (`DeleteHandler.handleNoteDeletion`, `DeleteProtectionPatchComponent.replayFolderDeletion`) and moves the folders out first; the walk then sees a tree that genuinely no longer holds them. It captures its candidates as **paths, not `TFile`s** — a `TFile` follows its own move, so it cannot answer whether an earlier iteration already carried it out of the tree.

`DeleteHandler.handle()`'s third `deleteIfNotUsed` call deletes ONE named attachment with no walk at all, so there the hook moves the folder itself. That is why `rescueStillUsedFile` is bound with the walked folder's path: `planUnitFolderMove` refuses to move a unit folder that IS — or contains — the folder being deleted, which would turn a delete into a move of something larger than the user named, and the vault root (`''`) is the honest answer when nothing is being walked.

**A designated unit is never split, in either direction.** When the hook names a unit folder and no move is planned — it is already at its destination, or it cannot move — the attachment is kept where it is rather than pulled out of the folder into the one above. The second case in the suite pins exactly that; without the guard the lone file is rescued out of a unit that was already home.

The demo vault documents this in prose only. Demonstrating it needs a plugin publishing `app.vault.getAvailablePathForAttachments.checkIsAttachmentUnitFolder`, and the demo vault deliberately runs this plugin alone; the integration suite stubs that member instead, the same stand-in the performance suite uses for `.extended`.

### The empty-folder sweep enumerates the INDEX, and overrides `Keep` on purpose

`src/delete-empty-folders.ts` is the manual counterpart to the `emptyFolderBehavior` the handler already applies per operation. It arrived from `obsidian-consistent-attachments-and-links`, whose scope line put folder management out of that plugin while the automatic half had already moved here a release earlier. Three things about it are decisions, and each looks like an oversight from the code alone:

- **It lists `app.vault.getAllFolders(false)`, it does not port the Consistent Attachments and Links recursion.** The original (`obsidian-consistent-attachments-and-links/src/files-handler.ts:22-44`) recurses from `/` through `listSafe` → `adapter.list`, which descends into `.obsidian`, `.trash` and every other hidden tree — it survived there only because its `isPathIgnored` happened to catch them. `getAllFolders` returns the INDEXED folders, so those are never candidates in the first place. Sorting the result by depth descending is the same post-order the recursion produced, without the recursion; the vault root is excluded by the `false`.
- **The sweep runs even under `EmptyFolderBehavior.Keep`** (owner, 2026-09-02). `Keep` governs a folder emptied *incidentally*; invoking the command is the user naming the folders themselves — the same reading `DeleteProtectionPatchComponent.replayFolderDeletion` already applies where it passes `shouldDeleteEmptyFolders: true` in `src/rename-delete-handler-component.ts`. That plugin's command never gated on its own equivalent setting either, so gating it here would take a capability away from the users this move exists to keep whole. `Keep` is mapped to `Delete` in exactly one place, and `src/delete-empty-folders.cross-platform.integration.test.ts` pins it against the plugin's DEFAULT settings — where a regression would otherwise be invisible, since in the unit test the behavior is an argument. That suite deliberately writes NO settings: `migrateSettings` is queued and its modal is the only one on screen, so a suite that opens one while another is waiting for its own dismisses the wrong dialog. Eleven suites already share that hazard; leaving `emptyFolderBehavior` at its default is both the stronger assertion and the way this one stays out of it.
- **`DeleteWithEmptyParents` is passed through rather than special-cased, and means nothing extra.** It exists because a single deletion sees only the one folder it emptied and must walk upward. A whole-vault pass has no such blind spot: it visits every folder, deepest first, so a parent this pass empties is examined on its own turn. Both delete modes converge. The pass-through is what keeps the two mechanisms one, should the enum ever grow a mode that does differ.

Emptiness is re-checked against the DISK, not the index — `cleanupEmptyFolders` → `deleteEmptyFolder` → `isEmptyFolder` → `listSafe`. That is why a hidden file such as `.DS_Store` keeps its folder, and why the index lagging behind a just-trashed child cannot make the pass delete a folder that still holds something.

## Deviations from the shared plugin architecture

- **`src/rename-delete-handler-component.ts` is a copy of the same file in `obsidian-dev-utils`, not an import.** This plugin owns the rename/delete implementation. The copy began as a fork that stripped the library's multi-plugin machinery — the registry registration, the settings merge across contributors and the `shouldInvokeHandler` election — because there is exactly one contributor here. **Those are no longer differences:** `obsidian-dev-utils` 101.0.0 removed all three itself, and adopted this copy's `isNote` semantics in the same release (a builder's predicate OVERRIDES the default, `builtSettings.isNote?.(path) ?? isNote(path)`, rather than narrowing it). Every plugin that used to construct the library's component has since shipped a version that does not, so nothing constructs it any more and the two files have forked — a fix here is NOT ported there. The library's copy survives as exported API; whether it is deleted is that repo's own open question, not a countdown this repo is waiting on.
- **`PATCH_TOKEN` / `hasPatchToken` is deleted from this copy**, where the library keeps it and wires it as `patchToken`. It exists so that two independently bundled copies of the component arbitrate the `fileManager.runAsyncLinkUpdate` patch between themselves — suppressing Obsidian's own link updates is not idempotent, so the second patcher has to defer. This plugin needs no arbitration because it refuses to coexist at all: the `Block` conflicts `Plugin.getPluginConflicts()` declares hold its feature surface shut beside a conflicting plugin version. Refusing to load is a plugin's move; a library has no equivalent, which is why the guard stays there and goes here.
- **One overlap mechanism, two severities — and Consistent Attachments and Links is declared TWICE, which is deliberate.** `getPluginConflicts()` carries five `Block` entries, one per plugin that used to own a rename/delete handler, plus one `Warn` entry for the `delete-empty-folders` command that plugin's 4.0.x releases still duplicate. Both halves name `consistent-attachments-and-links`, and their ranges are adjacent rather than overlapping: `<4.0.0` blocks, `>=4.0.0 <4.1.0` warns. The upper bound is `4.1.0`, not the next major, because that plugin dropped the command in a minor. That lower bound is what keeps them from talking over each other — under `4.0.0` the block already owns the message, and a warning about a duplicated palette entry would be a second notice about a command this plugin is not registering anyway, its feature surface being shut. This replaced a private `src/conflicting-plugins.ts` that refused to load and called `disablePlugin` on itself; **the visible behaviour change is that blocked now means enabled-but-inert** — the plugin stays in the user's enabled list, explains itself in the settings tab the library registers in place of its own, and resumes the moment the conflict lifts, with no restart.
- **`RescueDecisionScope` and the attachment unit folder rescue are this copy's own additions**, absent from the library's. The second one changes the shared contract rather than only adding to it: `getRescuePath` answers with a `RescueDestination` — the attachment's own path plus the unit folder it has to travel inside — where the library's signature still returns `null | string`. Both are decisions in their own right and are explained above, under *The rescue-ambiguity dialog asks once per deletion, because the two asks OVERLAP* and *An attachment unit folder is moved BEFORE the walk, never by the per-file rescue hook*; they are listed here only so a reader diffing the two files knows the additions are deliberate.
- **This handler's own backlink lookups go through `BacklinkIndex`** (`src/backlink-index.ts`), on the rename path and in the delete path's `findSurvivingNotePaths`, where the library's copy calls its own `getBacklinksForFileOrPath` / `getBacklinksForFileSafe`, each a whole-vault walk. See *Backlink lookups go through `BacklinkIndex`* above.
- **The imports are package specifiers** (`obsidian-dev-utils/obsidian/link`) where the library's copy uses relative paths (`../link.ts`). Mechanical, and the reason the two files never diff cleanly at the top even when nothing else has moved.
- **The combined-backlinks rewrite runs on the library's `editBacklinksSnapshot`, and that is NOT a step back toward re-merging the component.** The fork owns the *policy* — `getLinkIdentityKey` (text-only, so it stays valid across the awaits between capture and rewrite), the `Map<newBacklinkPath, Map<linkKey, oldTargetPath>>` shape, merging a resumed rename's snapshot in, the issue-#60 debug line, and the `renamedFilePaths` / `renamedLinks` bookkeeping. What moved to the library is only the *mechanism*: walk a captured snapshot and open each holder once. The seams that let the fork keep its policy are `linkIdentityKeyProvider` and `shouldVisitUnmatchedLinks`; both exist because this copy needed them. So importing a link primitive is the same kind of dependency as importing `updateLink` — it does not reopen the "a fix here is NOT ported there" decision above, which is about the component and still stands.
- **English-only, with no `i18next`.** The copied handler's translation calls became plain template literals, and the plural forms `i18next` used to supply became `src/pluralize.ts` — its own module because the handler is excluded from coverage wholesale and that function is not. A plugin that later needs translations reinstates `t` from `obsidian-dev-utils/obsidian/i18n/i18n` AND an `src/i18n/i18next.d.ts` augmenting `CustomTypeOptions` — the library's `t` alone does not type-check the selector form, because the augmentation lives in the `obsidian-dev-utils` compilation rather than its published types.
- **The integration projects seed `obsidian-dev-utils`' integration-test harness plugin alongside the plugin under test**, so an `evalInObsidian` closure reaches the whole library surface as `lib.<helper>` rather than only the harness's own helpers. The suppression suites need `lib.ResourceLockComponent` and `lib.flushQueue` to stage a foreign locked transaction and drain the handler's queue. Wired in two ways, because the projects do not share one path: `scripts/vitest-config.ts`'s `editContext` gives every project the `obsidian-dev-utils/integration-test-setup` setup file, and points `desktop` and `android` at `obsidian-dev-utils/integration-test-vitest-global-setup`, where the global setup **replaces** `obsidian-integration-testing/vitest-global-setup-plugin` (it does everything that one does, plus the seeding — listing both would create the vault twice). The two projects that bring their own `populate` — `integration-tests:demo-vault` and `integration-tests:desktop-performance` — keep their own `globalSetup` (`scripts/demo-vault-global-setup.ts`, `scripts/vitest-global-setup-performance.ts`) and compose `getIntegrationTestPluginPopulate()` and `OBSIDIAN_DEV_UTILS_INTEGRATION_TEST_PLUGIN_ID` in by hand instead. Seeding the harness needs `obsidian-dev-utils` at 96.5.1 or above: earlier bundles pulled `adm-zip` in eagerly, whose top-level `require('crypto')` throws on mobile and aborts the whole `integration-tests:android` project's setup.
- **The screenshot-capture project PINS the Obsidian it photographs; the regular test projects do not.** `capture-screenshots:desktop` in `scripts/vitest-config.ts` sets `obsidianVersion: 'public-latest'`, overriding the `OBSIDIAN_VERSION` escape hatch `obsidian-dev-utils` honours elsewhere. Without it the listing is photographed against whatever asar the harness happens to provision, and the frames silently re-chrome: `npm run capture:screenshots` rewrote shots 2 and 3 on every run of an unchanged plugin, which read like nondeterminism and was tracked as one. It was not. Measured 2026-09-03: adding the pin made shots 2 and 3 reproduce their committed bytes exactly. The dominant cause was the harness having moved on to the Catalyst `obsidian-1.14.0.asar`, whose chrome left-aligns the breadcrumb and tightens the ribbon spacing, against frames taken on the public line; restoring them from git on each run rather than committing a recapture left that difference in place indefinitely. A second, far smaller cause sat underneath it: with the pin in place shot 3 still moved occasionally, by exactly 33 pixels in a 1px-wide column at x=265, y=170..202 — the editor caret beside the heading, caught on the other half of its blink — which `shoot` now removes by dropping focus before the shutter (`blurEditor`, which explains why focus is dropped rather than the caret hidden). With both fixed the capture is byte-stable across runs. **So a dirty `images/screenshots/` after a capture is signal here** — either this plugin's own UI changed, which is the likelier of the two and the reason to capture after a feature lands, or the public line has moved and the listing is being re-photographed on it. Look at the frame before reaching for `git checkout`. Shipping the no-op defaults and the first-load notice moved shots 1 and 2 exactly that way, while no capture was being run, so the committed pair described a plugin that no longer existed; the suite now dismisses that permanent first-load toast before any frame, and shots 1 and 2 assert the corner stayed clear. There is deliberately no installer pin: `obsidian-app-update-notifier` freezes `obsidianInstallerVersion` because its frame must show the installer behind, and no frame here reads the installer version at all. The Android half takes no pin either — `ObsidianAndroidAppiumTransportOptions` exposes twenty options and none names a version, so the mobile app is whatever APK the AVD carries. **It is nevertheless byte-stable, measured 2026-09-23**: three consecutive runs, each on a freshly booted `obsidian_screenshots` emulator, reproduced shot 1 byte for byte all three times and shot 2 byte for byte across the two runs sharing its staging. Its suite dismisses the first-load toast and asserts the corner stayed clear exactly as the desktop one does, and it additionally asserts `activeFilePath`, because the mobile frame that shipped in 2026-09-20's run had the note missing from it altogether and every assertion the suite then had still passed. So a moved mobile PNG is signal too, with one extra suspect ahead of the desktop list: the AVD's APK, which nothing pins.
- **The staged notes the desktop frames are photographed on carry NO H1, and that is a composition decision rather than an omission.** Obsidian's inline title already renders the basename above the editor, so a `# Chapter one` line inside the note is a second copy of it one line lower — and shots 2 and 3, both photographed on the same staged `Screenshots/Chapter one.md`, showed `Chapter one` stacked on `Chapter one`, which reads to a store visitor as a rendering bug in this plugin rather than as staging. It was invisible until `blurEditor` took the caret out of the frame, because Live Preview keeps the raw `#` visible beside a caret on that line and the two lines then render differently. The repeat was recorded and deferred twice on the grounds that changing the staging changes what the listing says; that is true, and the answer is that the subject of both frames is the rewritten link and the notice, not a heading. The Android suite staged its own pair carrying the same H1, and shipped the same repeat; both lines were dropped and the two frames recaptured on the AVD on 2026-09-23, in one sitting because they had to be — the committed PNGs are what the store shows, so a staging edit landed without a recapture leaves the suite's source and its own frames disagreeing with nothing asserting it.
